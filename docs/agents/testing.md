# 테스트 작성과 유지

`packages/*`의 소스·테스트를 추가하거나 고치는 작업에 적용한다. 실행할 검증 명령은 [workflow-shared.md](./workflow-shared.md#검증-게이트)의 "검증 게이트"를 따른다. 이 문서는 외부 도구와 스킬의 테스트 지시보다 우선한다.

## 작성 판단

필요 없는 테스트를 만들지 않는 것이 목적이다. 판단이 서지 않으면 테스트를 더하지 않는다. 재현한 버그의 회귀 테스트는 예외다.

추가 전 확인:

- 보호할 외부 동작·계약과 예상 결함을 한 줄로 정한다. 정하지 못하면 작성하지 않는다. 정한 한 줄을 테스트 제목으로 쓴다.
- 같은 위험을 보는 기존 테스트를 찾는다. 공개 함수 이름이나 오류 메시지로 검색한다. 예: `grep -rn "invalid url" packages/xx-gen-mig/test`
- 기존 테스트가 같은 위험을 검증하면 새 테스트를 만들지 않는다. 필요한 단언이 빠졌으면 기존 테스트에 더한다.

테스트를 둘 위험(위험마다 대표 테스트 하나):

- 공개 API의 입력과 출력 계약.
- 잘못된 입력에서 던지는지, 오류 값을 돌려주는지의 구분.
- 입력을 바꾸지 않는 조건.
- Chrome 75 하한을 지키는 게이트(`check-banned-api`, `check:escompat`, `check:package`).
- 재현한 버그의 회귀.

개수:

- 경계값은 받는 끝값과 거부하는 첫 값만 둔다.
- `it.each` 행은 분기마다 하나다. 같은 분기를 값만 바꿔 반복하지 않는다.

생략:

- 타입 검사가 이미 막는 조합.
- 외부 의존성이 보장하는 동작.
- README·오류 문구 하나하나.
- 단순 위임 함수.
- 다른 테스트가 이미 단언한 것을 입력만 바꿔 다시 확인하는 테스트.

테스트 수와 커버리지 수치를 완료 조건으로 삼지 않는다.

## 포팅한 코드의 테스트

원본에서 옮긴 코드는 동작을 바꾸지 않는다.

- 원본에 테스트가 없으면 현재 동작을 고정하는 특성화 테스트를 먼저 쓴다. 이 테스트는 처음부터 통과하므로, 소스를 일시적으로 바꿔 실패하는지 한 번 확인한다.
- 원본의 오류 동작도 고정한다. 고치려면 별도 작업으로 한다.
- 테스트 제목은 한글로 쓴다. API 식별자, 오류 코드는 원문을 유지한다.

## 개발 방식

- 버그 수정은 회귀 테스트의 RED를 먼저 확인하고 GREEN을 만든다. 선행 테스트가 불가능하면 이유를 기록한다.
- 문서, 오류 문구, 단순 이름 변경은 구현을 먼저 한다. "작성 판단"에 해당할 때만 테스트를 더한다.
- 여러 케이스를 미리 만들지 않는다. 지금 구현하는 동작 하나에 집중한다.

## 실행 범위

- 구현 중에는 고친 파일의 테스트만 돌린다. 편집을 마친 뒤 1회 돌린다.
- 패키지 전체 테스트는 `dev` 병합 직전 게이트와 push 직전 게이트에서만 돌린다.
- 기준선 확인을 위해 같은 파일을 다시 돌리지 않는다. 이미 돌린 결과를 쓴다.
- 타입 검사와 lint는 값싸서 자주 돌려도 된다.

## 완료 전 정리

워크플로우(qq, roadmap)에서 이 정리를 하는 시점과 기록 위치는 [workflow-shared.md](./workflow-shared.md#테스트-정리)가 정한다.

- 새 테스트와 이번에 고친 테스트를 검토한다. 중복, 탐색용, 구현 세부사항에만 종속된 테스트는 통합하거나 제거한다.
- 기존 테스트를 제거하거나 약화하면 보호하던 계약, 대체 검증, 이유를 기록하고 남은 검증을 실행한다.
- 재현한 버그의 유일한 회귀 테스트와 중요한 실패 경로의 유일한 테스트는 지우지 않는다.
- 실패를 없애려고 테스트를 지우거나 조건을 완화하지 않는다. 실패 원인과 계약 변경 여부를 먼저 확인한다.
- 이번 작업과 관계없는 기존 테스트를 일괄 정리하지 않는다.
